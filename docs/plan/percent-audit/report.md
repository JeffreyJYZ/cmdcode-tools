# Lane P — percentage / limit audit (read-only recon)

Repo `/Users/jyz/dev/cmdcode-tools`. Every claim below cites `file:line` from the tree as read on 2026-11-23.

## Framing (load-bearing)

The endpoint's ~75% is **not** a defect. It is the accurate time-weighted utilization: the spend was made
against an $80 allowance for part of the period and $100 after, and the blend answers "how used up am I".
`spend ÷ today's cap` (69.7%) answers a different question, "what is left now". The server documents the
basis gap itself at `cmduse/src/ocuse/api.rs:19-22` ("the server meters with its own price basis"). The
change from $80 to $100 is recorded in-tree as the thing the live catalogue exists to fix:
`cmduse/src/ocuse/catalogue/tests.rs:56-57` — "The defect this module exists for: the limit is the
endpoint's, not $80."

Only three things are rankable as faults:

1. a percentage printed with no statement of what it is a percentage **of**;
2. a percentage converted back into a dollar cap, which is meaningless for a blend and feeds pace;
3. a cap that can change mid-window with no history recorded, so nothing can compute or explain the blend.

Nothing in this report recommends replacing a blend with `spend ÷ current cap`.

### 1a. `ocuse` — per-model Go limits

- **Source, live:** `GET /zen/go/v1/models` (`cmduse/src/ocuse/catalogue/mod.rs:4-10`,
  `cmduse/src/ocuse/catalogue/mod.rs:36`, `cmduse/src/ocuse/catalogue/fetch.rs` via `MODELS_URL`). The plan
  allowances come from the payload's `go.monthly_usage`: `cmduse/src/ocuse/catalogue/convert.rs:65-83`
  (plan ids discovered from the keys) and `cmduse/src/ocuse/catalogue/convert.rs:86-96` (each model's limit).
- **Source, baked fallback:** `core/zen.json:553-581` (`allowanceByModel`; DeepSeek V4.1 Flash is `100` at
  `core/zen.json:556`, i.e. already the raised value), parsed at `cmduse/src/ocuse/zen.rs:94-97` and read by
  `go_limit()` at `cmduse/src/ocuse/zen.rs:118-123`.
- **Resolved once per process, 6-hour cache TTL:** `cmduse/src/ocuse/catalogue/mod.rs:39-41`
  (`DEFAULT_TTL_SECS: u64 = 6 * 3600`), `:75-77` (`init`), `:103-146` (`resolve`: cache → endpoint → seed).
- **Applied to a model row once per report build:** `cmduse/src/ocuse/window.rs:319-328`, specifically
  `cmduse/src/ocuse/window.rs:324` — `limit: catalog.go_limit(plan_id, &row.model)`.

**Can it change mid-window?** Yes. The vendor raised the DeepSeek allowance in-period; a fresh fetch picks
up `$100` and the baked seed now carries it too (`cmduse/src/ocuse/catalogue/tests.rs:56-57`). A running
watch process keeps its answer for the whole run (`cmduse/src/ocuse/catalogue/mod.rs:73-77`), so the change
lands at the next start or after the 6-hour cache expires (`cmduse/src/ocuse/catalogue/mod.rs:39-41`).

**Detected anywhere?** Only as provenance, never as a value history. The catalogue origin and age are printed
at `cmduse/src/ocuse/render.rs:456-466`, in `--json` as `catalog` (`cmduse/src/ocuse/render.rs:884-887`) and
in `statusline --json` as `catalogSource` / `catalogAt` / `catalogAgeSecs`
(`cmduse/src/ocuse/render.rs:806-810`). Nothing stores `{model, from, to, at}`; nothing can compute a local
blend or say "the cap moved on this date".

### 1b. `ocuse` — the three account meters

- **Source:** `GET https://opencode.ai/zen/go/v1/usage` (`cmduse/src/ocuse/api.rs:36-37`), fetched at
  `cmduse/src/ocuse/api.rs:164-202`; the three `Meter` fields are `status`, `percent`, `resetsAt`
  (`cmduse/src/ocuse/api.rs:39-50`). The endpoint is authoritative by design
  (`cmduse/src/ocuse/api.rs:9-26`).
- **Can it change mid-window?** The reported percentage changes as the spend is weighted against a changing
  basis — that is the accurate blend, and it is the endpoint's own number. The local code never sees the

- **Detected?** The value is read on every snapshot and carried verbatim into `Report.account`
  (`cmduse/src/ocuse/window.rs:90-101`, `cmduse/src/ocuse/render.rs:513`). No cap-change event is recorded;
  the only explanation a user gets is the catalogue provenance line (1a), which says nothing about *when*
  the allowance moved.

### 1c. `cmduse` (CommandCode) — per-model allowances and account totals

- **`cmduse` has no per-model allowance table.** Its per-model report computes a share of *period spend*,
  not of a limit: `cmduse/src/report_render.rs:547-550`. The CommandCode per-model allowances live in the
  plugin's generated catalogue (`opencode-plugin/src/catalog.ts`, regenerated by `bun run extract:catalog`)
  and in `mpc` (`oc-cmd-compare/src/data/sources/cc/catalog.ts`); the plugin overlays a live copy of
  `models.md` from the npm CDN with a disk cache (`opencode-plugin/src/catalogLive.ts:36-38`, `:208-233`).
- **Account total (dollars):** `summary.total_cost` from the CommandCode account API
  (`core/src/wire.rs:75-89`, fetched at `cmduse/src/snapshot.rs:56-69`).
- **Account cap:** `plan_monthly_cap(&s.sub.plan_id)` (`cmduse/src/render.rs:2` re-export), backed by the
  baked `caps` table in `core/plans.json:14-25` (GOAT `70`, Pro `80`, Go `10`, …).
- **5-hour and weekly windows:** server-provided `used` / `cap` / `exceeded` / `resetAt`
  (`core/src/wire.rs:15-33`), printed with the cap as money at `cmduse/src/render.rs:468-496`.
- **Can it change mid-window?** The plan cap changes only when a release changes `core/plans.json`; the
  token is not a live cap source. The 5h/week caps come from the API and can move server-side.
- **Detected?** There is no blend here — the CLI computes its own share from the same cap it prints
  (`cmduse/src/render.rs:350-358`, `:436-444`, `:468-494`), so a cap change simply changes the number. No
  history of the old cap is kept (`core/plans.json:14-25` is a static table).

### 1d. `arkuse` — per-tier AFP monthly cap and the `arkcli` plan meters

- **Baked tier cap:** `core/ark.json:12-51` (`plans[].afp`: Small 20 000, Medium 100 000, Large 250 000,
  Max 500 000), hand-maintained (`core/ark.json:2`). The file itself records a mid-window change:
  `core/ark.json:305` — "upgradeOnly: no downgrade; the monthly quota is pro-rated, the 5h/weekly windows
  reset to the new tier immediately".
- **Server meters:** `arkcli usage plan --profile …` (`cmduse/src/arkuse/api.rs:220-264`). Each period
  carries `total`, `used`, `percent`, `reset_at` (`cmduse/src/arkuse/api.rs:185-200`); the server's percent
  wins whenever present (`cmduse/src/arkuse/api.rs:202-217`), and the meter is built from those server
  figures at `cmduse/src/arkuse/api.rs:248-253`.
- **Local fallback:** `cmduse/src/arkuse/render.rs:224-229` computes `local_pct = used.afp / quota × 100`
  and labels it `(est.)` at `cmduse/src/arkuse/render.rs:285-294`.
- **Detected?** Server `used` and `total` are read together from one answer, so there is no cross-source
  blend. The baked tier cap can go stale against a pro-rated upgrade (`core/ark.json:305`) and no cap
  history is stored. Crucially, pace uses the server's own `meter.used` and `meter.quota` directly
  (`cmduse/src/arkuse/render.rs:233-242`) — no percentage is inverted into a cap.

### 1e. `oduse` — plan caps and credit pool

- **Baked caps:** `core/od.json:17-69` (`monthlyUsd` / `weeklyUsd` / `fiveHourUsd`, plus the Go plan's
  `capOverrides` for DeepSeek V4.1 Flash: `$120/$30/$10` against the default `$220/$55/$18` at
  `core/od.json:27-37`). Selection is `cap_set_for()` (`cmduse/src/oduse/caps.rs:60-68`) and `cap_pick()`
  (stricter set wins, `cmduse/src/oduse/caps.rs:70-115`).
- **Server windows:** the app snapshot's `designPlanWindows` supplies `remainingCredits` and `limitCredits`
  (`cmduse/src/oduse/snapshot.rs:150-176`); `used_credits = limit - remaining` and
  `leftPct = remaining / limit` at `cmduse/src/oduse/snapshot_window.rs:15-30`. Both halves come from the
  same snapshot, so there is no blend and no back-solve.
- **Local windows:** `pct(used.credits, cap)` at `cmduse/src/oduse/render/windows.rs:43-59`, with the cap
  named on the row (`cmduse/src/oduse/render/windows.rs:53-57`) and in JSON as `limitUsd` / `leftPct`
  (`cmduse/src/oduse/render/json.rs:76-87`).
- **Can it change mid-window / detected?** The baked caps only move on a release; the server window can
  move its `limitCredits`, but it is read with its own `remainingCredits`, so no inconsistency arises.
  No history of a cap change is kept.

**Flag (a) — stale or implied denominator.** `implied_cap(spend, share_pct) = spend × 100 / share_pct`
at `cmduse/src/ocuse/render.rs:268-270`. It is called once at `cmduse/src/ocuse/render.rs:171` and its result
feeds `pace_eta` at `:172-180` and the monthly "by now" dollar figure at `:184-192`. The renderer
deliberately stopped *printing* that cap (`cmduse/src/ocuse/render.rs:211-215`) and the tests pin the
back-solved numbers (`cmduse/src/ocuse/render.rs:1744-1750`: 30 at 5% → 600, 30 at 59% → 50.847…). But the
fiction survives in the two printed figures it still produces. A blend has no single denominator, so a
$93.4 cap is invented exactly when the allowance moved.

**Flag (b) — numerator and denominator from different sources.** The account's 75% is server-computed;
the dollar beside it is this store's spend, re-priced on the documented peak/off-peak schedule

(`cmduse/src/ocuse/render.rs:273-280`), and the sidebar does the same (`opencode-plugin/src/sidebar/zen.ts:277-293`),

(`cmduse/src/ocuse/render.rs:866-878`). This is a labeling defect, not a wrong value.

**Flag (c) — a printed pair lets a reader derive an unpublished cap.** `· 75% of limit` sits next to

`cmduse/src/ocuse/render.rs:211-215` shows the author knew this; the pair still permits it.

## 4. Ranked recommendation

**Which binary actually has the bug: `ocuse` only.** It is the sole binary that (i) receives a blended
percentage from a server whose basis it cannot see, (ii) prints that percentage next to local dollars
without saying what it is a percentage of, and (iii) turns it back into a dollar cap for pace. `cmduse`,
`arkuse` and `oduse` each derive their own share from a cap they also print, or take `used` and `total`
from the same server answer; they carry only the *risk* of a mid-window cap change with no history
(finding 3), not the contradiction.

**Fix order:**

1. **`ocuse` — remove the cap inference first (fault 2).** `implied_cap`
   (`cmduse/src/ocuse/render.rs:263-270`) must leave both the display and the pace path
   (`cmduse/src/ocuse/render.rs:171-192`). Pace must use a published or historically weighted allowance and
   abstain when none exists. This is the only finding that manufactures a number the vendor never
   published.
2. **`ocuse` — label both percentages (fault 1).** Keep the server blend as the headline, print the
   `spend ÷ today's cap` figure beside it with its own label, and name the cap change in the output. The
   two figure pairs currently sit unqualified at `cmduse/src/ocuse/render.rs:216-223`, `:341-358`,
   `:438-447` and `opencode-plugin/src/sidebar/zen.ts:266-294,427-443`.
3. **`ocuse` — record cap history (fault 3).** The live catalogue is re-resolved with a 6-hour TTL
   (`cmduse/src/ocuse/catalogue/mod.rs:39-41,103-146`) but only provenance is kept
   (`cmduse/src/ocuse/render.rs:884-887,806-810`). Without `{model, from, to, at}` spans nothing can explain
   or recompute the blend locally.
4. **Then the other three — cap history only.** `core/plans.json:14-25`, `core/ark.json:12-51,305` and
   `core/od.json:17-69` can all change between releases; none records the old value. These are lower
   priority because no cross-source percentage is involved today.

The ocuse implementation is already scoped in `docs/plan/percent-audit/lane-q.md:34-77` (weighted
allowance helper, labelled current-cap figure, cap-change line, `percentSource` / `serverPercent` /
`currentCapPercent` fields, cap-history file and the test names); that brief ranks the same two faults
first and keeps the blend as the headline (`docs/plan/percent-audit/lane-q.md:22-30,34-53`).

**The one shared helper the fixes should use:** a pure function in `cmduse-core`, next to
`pct` (`core/src/lib.rs:121-131`) and `pace_eta` (`core/src/lib.rs:231`), that owns both invariants —
*a utilization percentage must carry the basis it was computed against* and *a percentage is never
inverted into a dollar cap*. Its result should expose the blend as the headline, the current-cap figure
as a separately labelled value, an optional "cap moved from X to Y" note, and a `pace_cap: Option<f64>`
that is `None` whenever the denominator is a blend with no known spans. All four binaries already import
`cmduse_core::{pct, money, …}` (`cmduse/src/render.rs:2`, `cmduse/src/ocuse/render.rs:11`,
`cmduse/src/arkuse/render.rs:11`, `cmduse/src/oduse/render/windows.rs:14`), so one helper prevents the four
renderers — and the plugin sidebar that consumes ocuse's text — from drifting back to a back-solved cap.
